# 反风控优化建议（讨论存档）

> 存档时间：2026-09-10；2026-10-22 更新实施状态
> 背景：用户担心求职自动化被 BOSS 直聘风控识别导致封号，以下是当时的讨论结论。
> 状态：**第 1、2 条已于 2026-10-22 实施**（见 `docs/dev-log.md` 当日条目）；第 3-6 条为行为约定，持续遵守。

## 前提共识

没有"绝对防封"的办法。BOSS 风控看的是**行为模式 + 设备指纹 + 频率特征**的组合，能做的是把机器特征降到接近一个谨慎的人工用户。

## 建议清单（按优先级）

### 1. 节奏随机化（✅ 2026-10-22 已实施）

~~当前投递间隔是固定秒数（`BossRecruitmentServiceImpl` 中 `TimeUnit.SECONDS.sleep(sleepTime)`），固定间隔是机器行为最典型的特征。~~

已落地：
- Java 旧链：`deliverJobs` 轮间固定 15s → **10-20s 随机**；`performDelivery` 配置等待时长 → **±40% 抖动（下限 3s）**；`simulateUserBrowsingBehavior` 固定 300px×3 → **次数/距离/停留全随机 + 1/3 概率中途驻足**。
- sidecar 主链：岗位间隔 `delayMs` → **±25% 抖动**；点「立即沟通」前新增 **2-6s 阅读停留 + 小幅随机滚动**；搜索/翻页滚动由固定 4 步 600px → **3-6 步、400-800px、1/4 概率中途驻足**。

### 2. 遇到验证立刻停，不要继续试（✅ 2026-10-22 已实施，决策权在 LLM）

~~当前弹窗 LLM 决策中，判出滑块/安全验证是 `IGNORE`——但 IGNORE 后流程继续跑，后续每个岗位都会撞在验证上，等于持续给风控喂异常行为。~~

已落地（决策权仍交给 LLM，不是硬编码规则）：
- Java 旧链：弹窗 LLM 新增 `PAUSE_TASK` 动作（安全验证/滑块/登录过期 → PAUSE_TASK），抛出 `SecurityVerificationException` 暂停整个投递任务，当前岗位保持待投递状态。
- sidecar 主链：`sendContact` 进页先做**风控信号采集**（geetest/captcha 选择器 + 正文关键词），命中即快速失败（不再空等聊天框 20 秒），信号随结果上报 `RISK_SIGNAL ...`；Python 侧 `run_contact_sender.adjudicate_risk_with_llm` 把证据交给 DeepSeek 裁决，判为验证/风控则本轮剩余岗位全部跳过（`SECURITY_VERIFICATION_PAUSE`，不计失败、不进已投递去重），人工处理后再跑。LLM 不可用时按强信号保守暂停。

### 3. 控制每日总量和时段

- 每天投递量保守，BOSS 本身有每日上限（工具已检测"已达上限"），**不要绕过**
- 只在工作时段跑（9:00~21:00），半夜批量操作显眼
- 不要多平台同时全开

### 4. 环境稳定

- 固定网络出口，别一会儿挂代理一会儿不挂——IP 剧烈变化比自动化本身更危险
- Cookie/登录态保持稳定、少重新登录（当前 Cookie 存库的做法正确）
- 浏览器指纹：已用 Patchright（patch 过的反指纹 Chromium），保持更新；不要混用原版 Playwright/Chrome

### 5. 内容侧

- 打招呼语每条不同（LLM 生成招呼语正好满足这一点，不要退回固定文本）
- 简历图片/附件不要每个岗位秒发，保持"先聊两句再发"的人工节奏

### 6. 监控封号前兆

出现以下信号 = 降权/风控预警，应停止运行几天：

- "异常访问"页面频繁出现
- 验证弹窗频率变高
- 岗位列表突然为空
